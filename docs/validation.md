# 验证方法与范围

## 现场实验：2026-11-13

设备为讯为 RK3568（4 GB 内存、32 GB 存储）与 OV5695；板端 Buildroot，
运行端为 VMware Ubuntu 24.04 / ROS 2 Jazzy。原运行时版本见 `config/upstream.json`。

摄像头先通过 V4L2 采集 1920×1080 NV12 单帧，经 OpenCV 解码后由原项目
图像适配器触发 `single_task/dock_a`。随后加入本仓库的连续 MJPEG 输入适配器。

连续实验接收 693 帧，首末接收时间跨度 138.382 秒，接收速率约 5.001 fps。
第 3 帧触发第一次任务，后续连续 370 帧持续展示没有重复触发；移开后最长连续
307 帧无映射标记，第 683 帧触发第二次任务，后续保持窗口没有第三次触发。
两条终态任务、SQLite 记录与两组 CAN 指令/响应匹配。

这些数字是首次现场集成验收的观测值，不是性能保证。时间来自运行端的单调接收时钟，
不是传感器曝光时间，不能据此计算端到端延迟。

## 未通过的探索轮次

第一次连续实验的两次任务都成功，但首次持续展示窗口只有 7 帧，没有满足验收要求
的至少 10 帧，因此保留 FAIL 结果。随后按“保持 → 移开 → 放回”重跑得到上述 PASS。
第一轮还观察到未配置的 ID 12，没有产生对应任务。

## 软件验证

- 固定上游的 11 个包构建与测试成功。
- `colcon test-result` 汇总为 499 条记录、0 errors、0 failures、83 skipped。
  83 条 skipped 来自 cppcheck XML。该总数包含运行器和代码检查，不能视作功能测试数量。
- 源码计数脚本报告 184 个 GoogleTest 声明与 59 个 pytest 声明。
- 上游七场景 E2E 通过：正常、故障、取消、STOP ACK 丢失、普通 ACK 超时、请求去重和统计。
- 发布版配置泛化后，使用独立构建目录和生成 JPEG 回放检查适配器与任务链路。

## 当前边界

真实硬件覆盖摄像头、RK3568 Linux 采集与网络传输。执行端采用 `vcan0` 和虚拟设备，
默认 ACK-only，成功表示设备协议确认。没有实测物理 CAN、真实执行器、停止距离或硬件急停。
连续流会在初始等待超时、后续无帧或超大帧等情况下退出，并尝试取消活动任务；
本版没有自动重连、常驻服务部署或板端任务面板。

CI 的 `replay_smoke.py` 使用生成图像，仅作为软件集成测试。CI 在 runner 支持 vcan 时
运行 E2E 与回放，不重复声明已做实体硬件实验。
